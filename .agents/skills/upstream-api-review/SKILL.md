# Copilot API Dashboard 上游跟进

对照上游 `caozhiyuan/copilot-api` 的变化与 Dashboard 的实际调用和数据流，回答是否需要更新、为什么，以及最小改动范围。

所有仓库路径相对项目根目录解析。执行输入为当前检出的代码、随仓库提供的契约样例和可获取的上游源码。

用户只要求检查时，保持只读，不自动更新代码或契约样例。用户已经授权适配时，沿用该授权推进；不要因为 skill 默认检查而重复要求确认。

## 确定比较对象

- 上游为 `caozhiyuan/copilot-api`；本仓库的 `origin` 是 Dashboard 自身，不能当成 API 上游。核对当前代码、配置和文档中的实际调用。
- 查看当前 HEAD、工作区改动、客户端和类型定义、聚合与存储代码，确认本次被检查的实现。
- 从 `internal/upstream/testdata/README.md` 的来源标注确定契约样例基线。若仓库未提供可确认的基线，直接将当前消费的契约与目标提交的源码逐项核对，并说明无法确定变化起点；不推测基线或要求补充外部历史记录。
- 读取 [项目参考](references/copilot-api-dashboard.md)，定位本仓库的接口、聚合、持久化和展示代码，再核对当前实现。

## 实时确认上游

同时确认最新发布版的 tag、发布时间、对应 SHA，以及用户关注的开发分支 HEAD。未指定分支时先查仓库默认分支。`target_commitish` 不是发布版的精确提交。

可通过 `gh` 或 GitHub 公开 HTTP 接口查询上游。使用 `gh` 时，例如替换下列提交或引用占位符后执行：

```sh
gh api 'repos/caozhiyuan/copilot-api/releases/latest' --jq '{tag_name,published_at,target_commitish}'
gh api 'repos/caozhiyuan/copilot-api/commits/REF' --jq '{sha,committed_at:.commit.committer.date}'
gh api 'repos/caozhiyuan/copilot-api/compare/BASE_SHA...TARGET_SHA' --jq '{status,total_commits,files:[.files[]|{filename,status}]}'
```

核对比较方向和基线是否覆盖当前实现，再读取相关变更及目标提交下的完整源码。发布说明只用来定位变化；桌面功能名称不能证明新增 HTTP 端点。结论和链接尽量固定到提交 SHA。

网页缓存、API 限流或认证失败时，可用独立的可用来源交叉确认，如 `gh api`、`git ls-remote`、精确提交的 raw 源码或临时目录中的源码快照。无需为检查修改工作仓库的 refs。无法确认最新状态时，明确已验证的版本和缺口，不沿用旧版本冒充最新，也不将工具环境的认证失败直接归因于用户登录失效。

## 沿调用链核对

先限定当前项目真正依赖的端点，再检查路由、鉴权、服务实现、统计查询和上游测试。重点确认：

- 方法、路径、凭据来源、请求头、参数、周期、分页、状态码和响应包裹结构。
- 身份与去重字段、必须存在的数据集、类型与可空性、单位，以及缺失、`null`、显式零的区别。
- 字段如何计算和解释，包括比例分母、时间分桶、时区、重置窗口、金额和计量单位。字段名和 JSON 结构不变仍可能影响正确性。
- 数据从上游到客户端、聚合、持久化和页面的路径；指出改变当前展示、历史快照还是后续采集。不要未经存储检查就要求迁移或宣称只影响新数据。

当上游网关只是转发或归一化另一个服务的数据时，涉及数值正确性的结论应回溯原始契约或权威客户端及其测试。不要只因新接口格式统一就认定它更正确，也不要以保持兼容为理由保留已证实的计算错误。

统计适配要确认可合并性：百分比通常应由汇总计数重算；平均延迟和速度需要有效样本数、权重或生成时间。信息不足时说明限制，不直接平均已有平均值。

区分已接入字段、新增可选字段和无关改动。不要把上游模型目录、页面布局或推理通道变化自动转成下游更新任务；先确认本项目是否维护对应映射或依赖其行为。

## 给出可复核的判断

先给结论，再用必要的简短表格或列表说明：上游变化、当前调用位置、实际影响、建议及源码依据。区分：

- 必须调整：会破坏现有行为，或已证实存在数据正确性问题；两者分别说明。
- 可选扩展：当前功能仍正确，接入后才会增加的新能力及其实际成本。
- 无需处理：已经适配，或变化与当前数据流无关。

标注检查时间、发布版与开发分支 SHA、比较基线。选择能验证相关假设的现有测试；没有相关变化时无需机械运行全套检查。单独说明本次实际执行的验证和未验证边界：源码检查、合成契约测试、隔离运行及真实实例联调各自证明什么。旧测试通过、构建成功或 HTTP 200 本身不证明真实集成正确。

检查请求到此结束；不因发现新功能就启动实现。

## 已获授权的后续适配

实施足以解决已确认问题的最小改动，复用现有配置和数据路径。契约样例及其来源、必要的回归保护和相关说明随实现更新；不要只改 fixture 版本号来宣称适配完成。

遇到必须由用户选择的统计含义、数据处理策略或新增范围时，先说明影响并澄清；其余已授权步骤继续执行。遵循用户关于不兼容重构的明确选择，不额外引入过渡机制。

按项目命令完成相关测试。若要求独立审阅，设计审阅与最终当前 diff 的代码审阅分别执行；不能用之前的设计结论替代当前实现审阅。是否提交、推送、创建 PR、部署及修改真实数据，仍由当前任务的授权决定。
